# M2 — Spring Batch 6 processor-skip adapter

The explicit RecoverableSkipListener resolves provenance via StepSynchronizationManager at each onSkipInProcess call. It uses a stable caller-defined occurrence identity, an explicit safe payload codec and sanitized error classifier. By default (transactional JDBC capture) the service calls captureInExistingTransaction; the JDBC repository wraps capture in PROPAGATION_MANDATORY to fail if its DataSource has no active transaction. Repository write operations remain REQUIRED and share the transaction. No REQUIRES_NEW. Errors propagate and fail the step.

Spring Batch 6.0.6 invokes the processor skip callback inside the sequential chunk transaction, after retry exhaustion and the skip policy accepts the skip. It does not invoke this callback for a null-filtered or successfully retried record. Write-skip scanning has different rollback semantics, so read/write capture is not implemented. Parallel processors do not share the chunk's thread-bound transaction and are unsupported; do not use a task executor, partitioning or remote step. For transactional JDBC mode require a persistent JDBC JobRepository, same DataSource instance and JdbcTransactionManager for repository and chunk; no mixed databases. Explicit memory mode supports one-shot resourceless jobs without transactional guarantees. The host must supply a deterministic codec and immutable input or safe snapshot; the listener observes the input after processor failure, not a preprocessor copy. No secret scanning, encryption or business validation is automatic.

VersionedPayloadCodec supports explicit decoders per schema version and a current encoder; no dynamic type lookup. The example CustomerPayloadCodec uses a fixed Customer DTO with Jackson 3. Unknown versions and oversized payloads fail. The example uses a checkpointed deterministic reader and JDBC writer. The application decides skip/retry policies. Registration is opt-in per step, and remains explicit when the starter is enabled. See [starter guide](starter.md).

See the example README for a runnable demo. The CI integration suite verifies 90 successes/10 captures, real fatal-writer rollback and restart, previous committed chunks, no capture for filter/retry success, fail-closed storage, and absence of capture without listener registration. JDBC integration tests additionally assert mandatory transaction enforcement and duplicate identity concurrency. Replay and worker state transitions are implemented; see [recovery engine](recovery-engine.md).

Reference: [Spring Batch 6.0 migration guide](https://github.com/spring-projects/spring-batch/wiki/Spring-Batch-6.0-Migration-Guide) and [6.0.6 ChunkOrientedStep source](https://github.com/spring-projects/spring-batch/blob/v6.0.6/spring-batch-core/src/main/java/org/springframework/batch/core/step/item/ChunkOrientedStep.java).

## Optional memory mode

The original transactional listener constructor remains the default. Explicit memory mode uses `CaptureSettings(..., false)` via the starter factory; it captures observed processor skips without a transaction and cannot guarantee rollback or durability. Use only a one-shot job and explicitly approve safe replay after completion. See [storage architecture](storage.md).
